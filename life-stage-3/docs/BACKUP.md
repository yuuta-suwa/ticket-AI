# D1 / R2 バックアップ・復元方針（Gate-0）

Sitesでは、コードを前のバージョンに戻してもD1/R2のデータは戻りません。そのため、アプリ独自のバックアップを使います。

## 何を保存するか
- 管理画面の「バックアップをダウンロード」で、1つのJSONファイル（`life-stage-YYYY-MM-DD.lsbackup.json`）を保存する
- 中身：D1の全テーブル（会員・承認状態・目標・ファイル情報）と、R2の画像本体（base64形式）
- R2の画像の実体が1つでも欠けていれば、バックアップ自体を失敗させる（欠けたまま保存しない）

## いつ取るか
| タイミング | 担当 |
|---|---|
| **Deploy versionを実行する前に毎回** | 管理者 |
| 週1回（決まった曜日） | 管理者 |
| D1のテーブル構造を変更する前 | 開発者 |

## どこに置くか
- 暗号化された保管場所に置く（例：FileVaultを有効にしたiMac、またはパスワード付きの保管先）
- 全会員の非公開情報を含むため、**Git・チャット・メールには絶対に置かない**（`.gitignore` で `*.lsbackup.json` を除外済み）
- 直近8世代を残し、それより古いものは削除する

## 復元の方法
- 管理画面の「復元」から、バックアップファイルを選ぶ
- **データが空のサイトにしか復元できない**（目標と画像が0件で、会員が管理者本人だけ）。既存のデータへの上書きや混在を防ぐため
- 本番で障害が起きたときの手順：
  1. 新しいSiteを作る（またはデータを空にする）
  2. `ADMIN_EMAILS` を設定する
  3. 管理者でサインインする
  4. 復元する
- 途中で失敗した場合：データを空に戻してからやり直す（復元は空のサイトが前提）

## 復元の訓練
- 月1回、ローカル（`npm run dev`）か検証用のSiteに復元し、次の3点を確認する
  - 会員数
  - 目標1件の内容
  - 画像1枚の表示
- 自動テスト `test/backup.test.ts` で確認していること
  - 復元後に目標・画像・承認状態が元に戻る
  - データが入っているサイトには復元できない
  - 一般会員と承認待ちの会員は実行できない
  - 改ざんされたファイルは拒否する
  - R2の実体が欠けていれば失敗する

## 限界と今後
- 1ファイルにまとめる方式で、上限は50MB程度。Gate-0では1会員20枚×1MBまでの想定
- フェーズA以降は、D1とR2を分けて、更新分だけを保存する方式に移る
- 復元は複数のSQLを順番に実行する方式。D1の一括実行（batch）への切り替えは、Sitesの実機で確認してから行う
