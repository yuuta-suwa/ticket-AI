# LIFE STAGE 2.0｜ログイン不要・2アプリ化 仕様変更指示書
版：1.0 / 作成日：2026-11-06
対象：Claude Codeで既存ソースを引き継ぐ開発者

## 1. 目的と変更優先順位
ユーザーが指定した今回の変更を最優先する。前回までの「メール認証後、権限に応じてコアタブを表示」は廃止する。
今回の依頼は変更仕様と引き継ぎ準備であり、この文書の作成によってアプリ変更・本番公開が完了したことにはならない。
教材の全面刷新、AI自動応答の新規接続、デザインの全面改修は今回に混ぜない。前回の教育構想は後続課題として保持する。

## 2. 確定した要求
| 項目 | A：既存アプリを変更 | B：新しく追加するアプリ |
|---|---|---|
| 仮称 | LIFE STAGE 2.0 統合版 | LIFE STAGE 2.0 全メンバー版 |
| 全メンバー向け機能 | 維持 | 継承 |
| コアメンバー向け機能 | 現在実装されている機能を維持 | 提供しない |
| ログイン・登録 | 不要 | 不要 |
| メール認証・ユーザー判定・会員ランク判定 | 廃止 | 設けない |
| 起動 | 直接ホームへ | 直接ホームへ |
| 配布 | 既存アプリを引き継ぐ独立URL | 新規の独立URL |

Aはコア専用ではなく「全メンバー＋コア」の両方を利用するアプリ。Bだけを追加し、合計2アプリとする。
Bではコアタブ、鍵マーク、アップグレード案内、コア教材へのリンク、統合版への誘導を表示しない。
ログインのないAはURLを知っている人が利用できる。配布先を限定しても、本人確認やURL転送の防止にはならない。秘密にしたい教材の閲覧制限はこの仕様では提供しない。

## 3. 実装前に確認する事実
この指示書では現行リポジトリ・本番DBを再検証していない。過去の会話にある実装・テスト報告は、現時点の動作証明として流用しない。
まず実コードを調べ、次を docs/current-state.md に記録する。
- 使用フレームワーク、起動・ビルド・テストコマンド、配置先。
- 全画面、ルート、ナビゲーション、API、教材の参照関係。
- ログインガード、セッション、会員ID・権限判定に依存する箇所。
- 回答・進捗・BOOK・カード・コアデータの保存先。
- 共同ルーム、メンター、共有リンク、管理機能、AIの実装有無。
- 「実装済み」「画面だけ」「未実装」「確認不能」の区分。
既存のコア教材・機能が未実装なら、今回完成済み扱いにしたり、推測で90日分を生成したりしない。存在するコア機能を失わず、残件を報告する。

## 4. 推奨設計（今回の実装既定案）
2つの独立した公開アプリを、共通ソースから作る。アプリが2つであることと、コードを丸ごと2コピーにすることは別。
- 全メンバー教材、入力UI、保存、BOOK、基本デザインを共通化。
- 統合版の入口だけがコアのルート・教材・ナビを取り込む。
- 全メンバー版の入口にはコアのルート・教材・APIを登録しない。
- 構成値はビルド／配備時に固定し、URLクエリや端末内設定から切り替えられないようにする。
- 既存の構造を活用する。大規模なモノレポ化やフレームワーク移行は必須としない。
- Bの配信物にコア教材、コア用チャンク、検索索引、静的JSON、公開ソースマップ由来のコア内容を混入させない。CSSやメニュー非表示だけで対応しない。
- 2つの独立したデプロイ先とoriginを使う。既存の公開先が確認できた場合のみAとして引き継ぎ、Bを新規作成する。名前やIDは推測しない。

## 5. 保存の仕様
認証なしで個人の記録を扱う簡易版の既定案は、端末・ブラウザ内保存とする。サーバーの全利用者共通レコードへ保存しない。
- ワーク回答、カード承認、進捗、BOOK、個人の計画・振り返りをIndexedDB等に保存する。
- 保存処理を共通の保存層へ集約し、画面に旧認証IDへの依存を残さない。
- キー例：life-stage2:integrated:v1 と life-stage2:members:v1。originに加えてアプリ種別で分離する。
- メールアドレス・氏名の登録を必須にしない。匿名認証サービスによる隠れたアカウント作成も既定では導入しない。
- 入力後に自動保存。保存完了前に「保存済み」と表示しない。保存失敗時は入力を保持し、再試行・バックアップへ進める。
- JSONバックアップと復元を両アプリに用意。schemaVersion、appVariant、exportedAt、教材／ワークIDを含める。
- 復元前に型・形式・容量・対応バージョンを検証。内容のプレビューと既存記録への影響を示す。既存記録を無言で上書きしない。
- AからBへの復元では全メンバーの許可された項目だけを受け入れ、コア記録を除外したことを示す。BからAへは共通部分だけを反映し、Aのコア記録を消さない。
- BOOK/PDF等の既存出力を維持。印刷を使う実装なら「印刷／PDF保存」と正しく表示する。
- 初回と設定で短く説明：「記録はこの端末・ブラウザに保存されます。端末変更やブラウザデータ削除に備え、バックアップしてください。」
- 同じブラウザを使う別の人とはデータが分かれない。設定にバックアップと、このアプリだけのデータ削除を用意する。削除は確認を挟む。
- 複数端末の自動同期、本人確認、運営側の個人別進捗一覧は、この保存方式では成立しない。

## 6. 機能を維持する際の対応表
| 既存機能 | 今回の対応 |
|---|---|
| 教材・プレゼン・ワーク | 既存内容とIDを保持。Aは共通＋実装済みコア、Bは共通のみ |
| 自動保存・再開・進捗 | 端末内保存へ移行 |
| 発見カード・本人承認・BOOK | 端末内の本人操作として維持 |
| コアの計画・KPI・振り返り・練習 | 実装済み範囲をAに維持し、保存依存を移行 |
| 練習タイマー等の端末完結機能 | 維持 |
| 相談文生成・コピー等の既存AI補助 | 現状を維持。新たな有料API接続を追加しない |
| メンター面談の個人メモ・予定 | 端末内で維持。予約の送信や相手側の確定と混同しない |
| メンターに見せる記録 | PDF／JSON等、利用者が選んで書き出す方式を既定案にする |
| 共同ルーム・他人の投稿・コメント | 本人確認に依存している場合は単純な認証解除不可。現行機能と代替案を差分に記録 |
| 期限付き共有・共有撤回 | 個人の認証に依存する場合は従来どおりの維持を宣言しない。配布済みファイルは撤回できない |
| 運営管理・権限付与・全会員データ閲覧 | 公開アプリには開放しない。管理面の認証は、利用者ログインの廃止と分けて扱う |

「機能維持」は、私的な個人記録や管理機能を誰にでも公開する意味ではない。
共同ルーム等が実際に使われている場合、個人用ファイル出力は完全な代替にならない。その機能を黙って削除・完成扱いにせず、旧環境を保持し、変更版はプレビューまで進める。差分と必要な決定を具体的に報告し、本番切替前に解消する。独立して進められる2アプリ化・個人ワークの実装は続ける。

## 7. 既存データの保護・移行
認証廃止はDBの公開許可を意味しない。
- 旧DBのアクセス制限を緩めない。旧の個人記録、メールアドレス、メンター記録を新しい公開アプリから取得しない。
- 固定の共通ユーザーID、共有サービスアカウント、公開管理キーで旧保存処理を代用しない。
- 旧テーブル、ユーザー、既存記録を削除しない。旧認証環境と復旧可能なソースを保持する。
- 教材の抽出では個人情報を含まないことを確認する。
- 既存ユーザーの私的記録を新アプリへ自動配布・自動ダウンロードしない。
- 移行が必要な場合は、旧環境で本人が出力したバックアップを新環境で本人が取り込む。出力経路がなければ、それを移行残件として記載し、無認証の一括移行APIを作らない。
- 旧URLのブラウザ保存、キャッシュ、サービスワーカーに過去の私的データがあるか調査する。無認証ホームで自動表示しない。自動削除もせず、必要な移行案を報告する。

## 8. 画面・遷移
A：ホーム→全メンバー学習／既存コアエリア→ワーク→保存→BOOK。
B：ホーム→全メンバー学習→ワーク→保存→BOOK。
共通：設定→バックアップ／復元／この端末の記録削除。
- 起動、再読み込み、深いリンクでログインページへ飛ばない。
- login、signup、callback、password-reset等の旧利用者認証URLは適切なホームへの転送か廃止画面にする。認証APIが動き続けないよう確認する。
- Bの既知コアURLは未提供として404等で応答し、コアの内容を描画しない。SPAなら未提供画面にして内容を配信しない。
- 配色・余白・高級感・既存共通UIを維持する。教材全面変更と同時に行わない。
- ホーム画面追加に対応している場合はアプリ名・manifest ID・start URL・キャッシュを2アプリで分離する。

## 9. 実装手順
1. 既存作業を保全し、変更用ブランチを作る。無関係な変更を上書きしない。
2. 現状調査と機能一覧、認証依存、移行リスクを記録。
3. 共通UIとデータモデルを再利用し、端末内保存・バックアップ・復元を実装。
4. Aの利用者認証／権限ガードを除去し、全メンバーと既存コアを利用可能にする。
5. Bを同じ基盤から構築し、コアのルート・教材を配信対象から除外。
6. 旧私的データと管理機能への接続が残っていないか確認。
7. 両ビルド、テスト、スマホ画面、ネットワーク要求、配信物を検証。
8. 2つのプレビューを作成できる環境なら作り、機能差分と移行／復旧手順を提出。
9. 本番切替はデータ移行と未解決の機能差分を整理した後に実施。公開先の権限がなければ、ユーザー用の具体的手順を提出し、公開済みと記載しない。

## 10. 受入条件
- [ ] A/Bとも新規ブラウザで、メール・パスワード・会員登録なしに利用開始できる。
- [ ] Aで全メンバー機能と実装済みのコア機能を利用できる。
- [ ] Bでコアタブ・案内・リンクが一切表示されない。
- [ ] Bの直接URL、検索、JSON、JSチャンク、APIからコア内容を取得できない。
- [ ] URLクエリ、localStorage変更等でBをAへ切り替えられない。
- [ ] 回答→再読み込み→再開→カード→BOOKが両アプリで成立する。
- [ ] AとBの記録が混ざらない。別ブラウザには個人記録が自動表示されない。
- [ ] バックアップ→復元が成立し、不正形式／未対応版／コア混入を安全に処理する。
- [ ] 保存不能時に入力を失わず、成功表示をしない。
- [ ] 新アプリが旧個人データ・管理APIを無認証で読めない／書けない。
- [ ] 新アプリが旧認証サービスへ自動登録・認証要求を送らない。
- [ ] 管理秘密情報がブラウザ配信物にない。
- [ ] 既存共有・メンター機能の変更と未実装箇所が正確に報告されている。
- [ ] モバイル幅で操作でき、BOOK出力が読める。
- [ ] 既存テストを確認し、変更に必要なテストを追加して両ビルドが成功する。
- [ ] 旧版へ戻す手順と、戻しても端末内記録が旧DBへ自動同期しないことが記載されている。

## 11. 完了報告の形式
Aの確認URL／Bの確認URL、変更一覧、維持できた機能、変更した機能、未実装・未確認、実行した検証と結果、旧データの扱い、バックアップ手順、本番反映・復旧手順を報告する。
URLがない場合はローカル確認用の正確なコマンドを示す。実行していないテストを成功と記載しない。
