採用デザインは **STRATEGY ATELIER（会話で表示した2番）** に確定。`docs/DESIGN_SELECTION.md` と `reference/design/strategy-atelier.png` を実装の基準とする。他の案への再選択は不要。

## 目的
「Instagramの投稿や報酬を入力する管理画面」を、**自分の状況を理解し、収益の制約を見抜き、何を変えるべきか一緒に決め、実施結果から提案を磨く専属AIコンサルタント** に変える。フォロワーが少なくても検証できる収益構造と、本人が商品販売をしない収益経路も必須で比較する。

「感動するデザイン」は、派手な装飾や偽の成果演出で作らない。最初の画面で「私の何を理解し、何が分かり、次に何をすればいいか」が伝わること、そして細部まで美しく使いやすいことを両立する。

## 手順
### A. 基線を壊さず理解する
- ソース構造、API、DB、認証、環境依存、会計・承認ルールを確認する。
- `source-snapshot-manifest.json` と照合し、勝手に別プロジェクトをゼロから作らない。
- 依存はロックファイルを優先して導入する。環境不整合があれば原因を特定し、無関係な依存の全面更新をしない。
- 元の環境が再現できない場合も、認証・DBを削除して動いたように見せない。境界を切り出す移植案を `docs/PORTABILITY_DECISION.md` に記録し、最小限の変更で作業を続ける。
- 最初の型チェック、ドメインテスト、DBテストを実行し、失敗の基線を記録する。

### B. 見た目より先に相談体験を設計する
- 初回は目的・強み・対象者・使える時間・収益化条件を、短い段階入力で整理する。
- 情報不足なら、スコアを捏造せず「今はここまで分かる」「次に必要な情報」を伝える。
- 継続利用時の最初の画面は、広告的な大きなヒーローではなく、実績に基づく戦略ブリーフと最優先の一手を中心にする。
- AI相談で生まれた結論を、根拠・仮説・施策・観測指標・停止条件として残し、施策や投稿の下書きに渡す。
- 実施結果が変わったら、前回の予測・判断との差、継続/修正/中止の理由、次の小さな検証を残す。

### C. デザインを実装する
- 採用済みの `reference/design/strategy-atelier.png` を最優先し、`strategy-atelier` のトークンで統一する。他の方向は比較案としてのみ残す。
- 画像そのものを背景に貼った「アプリ風の絵」にしない。文字、入力、ナビ、結果、施策作成は本物のHTML/Reactコンポーネントにする。
- 単なる色替え、カード大量配置、背景のAI球体、ダミーの収益グラフ、読めない小さい英語で高級感を装うことは禁止。
- ダッシュボード、AI相談室、収益戦略、投稿と検証、設定・接続を一貫したデザインで揃える。
- モバイルで意思決定と承認が完結する。長い入力は段階化し、指で押せる範囲、固定CTAとキーボードの重なりを確認する。
- 全体のCSSに修正を追記し続けず、共通トークンとコンポーネントに整理する。

### D. 機能の最小実装と互換性
- 既存のState v1を失わない。新しい相談データは移行可能な形式で追加し、旧JSONバックアップを検証する。
- 新しい相談出力は `docs/consulting-report-v2.schema.json` を出発点として検証可能にする。v1の既存レポートを破壊しない。
- 事実、仮説、提案、利用資格未確認、計測不能を分離して表示する。
- API未接続、ルール診断、外部AIからの取り込み、実際の生成AI実行を混同しない。
- 初期状態では有料AI・自動実行・公開を有効にしない。デモは実績へ保存しない。
- 投稿を承認した版と公開内容を紐付ける。変更したら再承認。外部素材URLの中身は固定されないため、変更検知/不変ストレージ等の対策を設計し、対策なしなら限界を明示する。
- 公開済み履歴、取消・減額、費用、工数、重複防止を残す。

### E. 完了まで検証する
- 型、既存14件のドメインテスト、3件のDBテストを通す。
- 新しい相談・根拠・施策引き継ぎ・旧データ移行・費用制限のテストを追加する。実装をなぞるだけのテストは作らない。
- 390/768/1440pxで、初回設定→相談→根拠確認→施策の下書き保存→観察結果登録→再診断を操作する。
- キーボード、フォーカス、コントラスト、長文、読込み、失敗、空データ、競合、接続切れも確認する。
- 有料の本物のAPIやInstagram公開を、ダミーやモックの成功と混同して「検証済み」としない。
- スクリーンショット、検証結果、残った制約、起動方法を提出する。

## 実装順と自律性
`docs/06_PLAN_AND_ACCEPTANCE.md` の段階で自律的に進める。フォント選びやコンポーネント整理など通常の判断ごとに、私へ「続けてよいか」を聞かない。既存の作業を保持し、失敗したら原因を解消して進める。

外部サービスのアカウント、認証方式の本番切替、料金が発生する操作、外部への送信、既存データの破壊などは、実際に必要になった段階で対象を具体化する。できる実装と検証を終えてから、私が必要な設定や判断をまとめて説明する。ブラウザー操作やCLIの権限機構は守り、権限チェックを無効にしない。

未接続機能をそれらしく動かして完成扱いにしない。本番への無断の差し替えやURL移行はしない。今回の最初の完成点は、既存の保護を維持し、相談の主要導線がローカルで動き、移設の差分が説明できる状態です。
