# 事業台帳 v0.2.0｜実装仕様と使い方
確認日：2026-10-24。

## 実装の位置

AI_Company_OS/src/revenue.mjs が既存CompanyのSQLite接続を使います。
既存テーブルを消さず、revenue_campaigns、revenue_leads、revenue_orders、revenue_payments、revenue_time、revenue_jobs、revenue_refund_reviewsを追加します。
DB変更前に実データをバックアップしてください。既存の業務履歴とは別の表で、会社の監査イベントへ記録を残します。

これは信頼された本人のローカルCLIです。本人のログイン確認を実装したWeb APIではありません。
実際の注文、顧客、入金、使用の存在を自動検証しません。証憑を本人が確認して参照を入力する方式です。
顧客の特定、支払事業者の照合、銀行着金、会計の収益認識、税計算を代行しません。

## 実行方法

AI_Company_OSでNode.js 24以上を使います。

~~~bash
node src/revenue-cli.mjs demo
node src/revenue-cli.mjs status
node src/revenue-cli.mjs campaign < campaign.json
node src/revenue-cli.mjs qualify < qualification.json
node src/revenue-cli.mjs economics < order-id.json
~~~

demoはメモリ内のsimulation区分を使います。ファイルの実績台帳を汚しません。
statusはdata/company.sqliteを開き、real区分の入力記録だけを集計します。新規DBなら空の実績として表示します。
JSONを標準入力で渡します。識別情報のないテンプレートを docs/revenue-input-templates/ に入れています。実データはアクセスを限定した場所で作成してください。
テンプレートはそのまま実績に登録せず、本人が確認した事実だけを入力してください。動作を見るだけならdemoを使います。

## 操作

| コマンド | 用途 |
|---|---|
| campaign / lead / qualify | 営業の単位、見込客、根拠のある適合確認 |
| order | 版と金額を固定した合意範囲の登録 |
| payment | receiptまたはrefundの証憑記録 |
| inputs / approve / revoke | 素材、対象版・期限付き制作許可、取消 |
| start / claim | 永続制作ジョブの1件登録と実行開始時の再確認 |
| artifact / qa / accept | 成果物の版、内部品質確認、顧客確認 |
| deliver / usage | 最終納品と実使用を別に記録 |
| time / campaign_time / campaign_costs / order_costs | 失注を含む営業時間、営業現金費用、制作時間、実原価の確認 |
| economics / status | 注文と全体の検証状況 |
| cancel / refund_review | 未着手の注文取消、返金原因と是正策 |

scope_hashはorderの戻り値を使います。artifact_hashは実ファイルから計算したSHA-256を使う運用です。
現段階の台帳は渡されたhashの形式と一致を確認するだけで、ファイル内容を取り込んで再計算しません。別物のファイルを登録できないようにするサーバー実装は次の作業です。
証憑参照は確認可能な記録へのIDやパスです。秘密情報の本文や決済番号の全桁を入れません。

## 状態と制御

SCOPED→PRODUCING→INTERNAL_REVIEW→CUSTOMER_REVIEW→DELIVERED→USED。
未着手かつ正味受領0の注文だけCANCELLEDへ進めます。入金・返金・素材・許可は、それぞれ別レコードや項目で管理します。
状態名PAIDだけで処理を進める設計ではありません。支払参照ごとの実際の受領・返金記録を照合します。

開始とジョブ取得の両方で、停止中でない、素材が揃う、制作許可の範囲と素材が現行、許可期限内、全額受領を確認します。
同じ支払参照、注文ID、時間記録IDの再入力は同じ内容なら再登録しません。内容が異なれば拒否します。
1注文の制作ジョブはDBで1件に制限し、同時取得もトランザクションで防ぎます。
ジョブの状態は永続化しますが、新しい制作ジョブのリース、クラッシュ回復、外部処理の照合は未実装です。
許可を取り消しても、既に送信した推論や外部操作が取り消されたことにはなりません。

## 採算

人の時間はminutes×hourly_yen/60で評価します。営業キャンペーンの未受注活動を除外しません。
獲得費は、各顧客の最初の全額支払注文へ配賦します。追加注文で新規顧客数を増やしません。返金でも獲得費を消しません。
獲得0社の費用は全体採算に残します。受領のある取消・全額返金注文の実費も全体へ残します。
実費、制作時間、営業時間、営業の現金費用が未確認ならeconomic_contributionはnullです。
数値が出ても税・固定費控除前で、本人の入力に基づく経済コストの集計です。監査された会計利益ではありません。

## 判断ルール

real区分だけを対象に、別顧客3、実使用2、使用済み顧客からの有料再注文または紹介経由の有料受注1、全コスト確認、残額率30%以上の注文2、全体残額プラス、返金原因確認済みを暫定の拡大候補条件とします。
使用確認後の再注文・紹介であることを、注文登録時点で保存します。後から紹介元を書き足して過去の需要実績を変えません。
条件が揃ってもLIMITED_EXPANSION_CANDIDATE（小規模な拡大の検討候補）です。business_successは常にUNVERIFIEDです。
顧客IDの同一性は本人の記録に依存します。独立した企業との取引を機械的に証明していません。
realという区分名は証拠の真偽を保証しません。テスト内のreal区分の架空入力も市場実績ではありません。

## 今後接続するもの

1. 顧客情報、権利、保管期限、申込・素材・発注合意の入力画面と注文IDの連結。
2. 認証された本人用APIとスマホ画面。権限をサーバー側で固定し、停止・取消・許可の現在値を再確認。
3. 制作workerとeveの接続、実際の成果物ハッシュの検証、ジョブの復旧・費用上限。
4. 決済イベントの真正性、照合、重複・遅延・順序違い・返金、口座着金の確認。
5. 顧客別配信と受領、用途に沿った通知、Obsidianへの匿名化した教訓の出力。
6. データのバックアップ、復元、保存期限、削除、実機iPhoneからの一連の確認。

全てを完成させるまで販売を待つ必要はありません。最初の1件は本人が商談・照合・送付し、台帳に記録できます。
反対に、このCLIが動くことだけで自動販売やスマホ運用の完成とはしません。
