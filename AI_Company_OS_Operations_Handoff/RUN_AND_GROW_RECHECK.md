# 既存サービス運営と新規開発の再点検
確認日：2026-10-24。対象：v0.4.0の仕様、ローカル台帳、実行指示。
結論：事業方針には検討価値があるが、現在の成果物をそのまま有料サービスの継続運営へ投入する判断はしない。
既存提供を守りながら新規を育てる要件は未達。コード試験の成功と、事業・並行運営の成立を区別する。

## 魅力と採算
AIで市場調査・試作・改善の手間を減らせる可能性と、継続利用から学べる運営モデルには検討価値がある。
ただし顧客はAI会社の組織図に代金を払うのではなく、個別商品が解決する課題に対価を払う。その需要と差別化はまだ実証されていない。
商品生成が容易でも、獲得・提供・保守・問い合わせ・契約責任まで低コストになるとは限らない。
サービス数が増えるほど、運営費と将来の履行責任は積み上がる。新サービス数を成功指標にしない。
毎回無関係な市場へ広げる前に、既存顧客の課題や共通の運営能力を活かせる隣接案もAIが比較する。

## 模擬実行で再現した3つの不足
再現：AI_Company_OS/scripts/audit-operating-gaps.mjs
出力：AI_Company_OS/examples/operating-gap-audit.json
すべてメモリ内の架空シナリオ。実顧客の停止や実請求を観察した結果ではない。

| シナリオ | 観察した現行動作 | 判断 |
|---|---|---|
| 既存サービスをACTIVEのまま、新実験を開始 | Active venture limit reached | 実験と稼働サービスのライフサイクルが分離されていない |
| 新規実験の費用結果をUNKNOWNとし、別事業の保守費を予約 | Reconciliation required before further spending | 安全側の全社保留により、保守の追加予約も止まる |
| 実験期限を過ぎた事業の保守費を予約 | Venture not active or learning deadline expired | 実験期限が継続運営の資金制御へ流用される |

これは試作の保守的な資金制御を、長期・複数サービスへそのまま転用できないことを示す。
既存82件のテストは引き続き成功。これらは実験台帳の制御を確認するもので、並行運営の完成を確認するものではない。
今回、資金ガードを弱める変更や、実行アダプターの接続はしていない。不足は未解決として実装指示へ反映した。

## 運営を3レーンへ分ける
| レーン | 仕事 | 優先と制限 |
|---|---|---|
| RUN 既存提供 | 稼働、納品、利用権、課金更新、問い合わせ、返金・解約、セキュリティ | 顧客への約束を守るための資金・担当・復旧経路を先に確保 |
| IMPROVE 既存改善 | 不満の原因除去、導入改善、既存商品の機能と販路の改善 | 顧客価値・障害リスク・費用を比較し、小さい変更で検証 |
| EXPLORE 新規探索 | 市場調査、新商品・サービスの試作、需要検証 | 既存の提供責任を差し引いた余力で実行。初期の活動中実験は1件 |

探索は続けられても、新商品を常に公開する義務は置かない。
重大な障害、誤課金、期限超過の問い合わせ、提供原価の不明があれば、不要不急の新規公開・広告拡大を保留する。
修正・セキュリティ対応・顧客への提供まで止める単一の新規開発停止ボタンにしない。
共通鍵の漏えい、全社資金の不明、共通決済基盤の異常等は全体対応が必要。問題を必ず局所化できるとは仮定しない。

## 資金と作業量
新規に使える金額は、本人の承認枠と確認済み資金から、既存の支払義務、返金等の必要準備、障害対応余力を考慮して判断する。
売上の入金を全額再投資せず、未提供分の責任と将来課金を残す。
月次の運営予算と事業開発の累積投資を分ける。過去の実費は消さず、運営の次期予算を本人の方針内で明確に許可する。
予約・実行中・不明結果は引き続き全体資金の露出へ含める。
不明な費用があるからといって、ガードを削除して別事業の支出を無条件に許可してはいけない。
他レーンの継続は、事前確保済みの枠、外部側の課金上限、共通資金の整合性、限定された権限を確認できる場合だけ。
将来支払の最大額が分からないなら、追加実行を保留して本人へ具体的な照合・対応を上げる。

固定の70%・20%・10%等を根拠なく設定しない。実際の問い合わせ量、保守工数、推論・実行枠、現金と将来支払から余力を計算する。
一つの大きな開発ジョブが監視・通知・サポートの実行枠を使い切らないよう、キュー、資金、権限、実行数を分離する。
AIで解決できない例外の頻度と本人対応時間を測り、対応できない量の商品を販売しない。

## 顧客満足と高評価
| 観察するもの | 計測する内容 |
|---|---|
| 価値実現 | 顧客が期待した作業を完了できたか、最初の価値までの時間 |
| 安定提供 | 重要操作の成功、遅延、納品期限、障害と復旧 |
| 顧客対応 | 約束した時間内の初動と解決、未解決の件数と滞留 |
| 継続 | 再利用、更新、再注文、解約理由 |
| 不満 | 返金、苦情、再発、改善後の再確認 |
| 声 | 満足度と回答者数、回答率、率直なレビュー |

稼働しているだけで顧客価値があるとはしない。星評価だけを最大化せず、実使用と不満の解決を優先する。
利用者の声→原因分類→修正案→小さな変更→結果確認を既存商品の改善バックログへ。
レビューは実際の利用経験に基づく任意の投稿。好意的な回答だけを集めて満足度を作らない。
Google Maps等を使う場合は媒体の現行ルールを確認。例えばGoogle Mapsは否定的なレビューの抑制や肯定的なレビューだけの選択的依頼を禁止している。これは全媒体共通の規約説明ではない。

SLOはサービスごとの顧客に重要な操作を対象に、目標・観察期間・測定範囲を決める。
数値は顧客への約束と経済性から設定し、一律の稼働率を保証しない。観測が古い・欠落なら健全と判定しない。
新しい公開を止めて信頼性を優先する判断を、計測と明示した方針で行う。

## 次に実装すること
1. 実験とは別に稼働サービスを登録し、RUN/IMPROVE/EXPLOREの状態・予算・責任を分離。
2. 監視・顧客対応・将来支払と本人例外への経路を接続。未確認は未確認と表示。
3. 初回の1商品で購入→提供→実使用→課金更新/解約・問い合わせ→全費用の経路を通す。
4. 既存サービスを維持した状態で新実験を走らせ、片側の故障、費用不明、容量不足を注入して確認。
5. 実測の運営負担を含めても余力が残る場合に、2つ目の公開へ進む。

独立した台帳を増やすことより、既存の台帳・worker・公開サービス・外部イベントを一巡接続することを次の開発単位とする。
顧客0の初回公開は過去の運営実績を捏造せず、運営準備を確認して小規模に提供する。
有料サービスが始まった後は、単純な実験期限・活動中実験枠をそのまま継続運営へ使わない。

## 実証まで言えないこと
魅力的な商品か、顧客満足が高まるか、継続黒字か、本人の介入が小さいか、並行運営が安定するかは、実サービスの観察が必要。
市場調査を行うソフトの存在と、売れる商品を繰り返し生む能力は別の実証対象。
現段階では、常時の無人経営や利益を保証する判定は出さない。
