# AI Company OS 1.0｜詳細設計
## 0. 今回確定する設計
「会社＝目的・資源・運営規程」「部署＝成果責任を持つ単位」「社員＝職務・権限・記憶・道具を持つ実行主体」「基盤＝指示・実行・検収・費用・記録を管理するプログラム」と定義する。

ゆうたさんはオーナー。AI社長が日常の運営を担い、8部長、16課長、16担当、監査役の42職務を登録する。42人を常時稼働させる設計にはしない。必要な仕事がある社員だけ呼び出す。

## 1. 実現する体験
オーナーが目的と制約を伝える。AI社長が事業・部門の目標に分ける。部長は課ごとの成果と予算配分を決める。課長は完了条件と入力を整え担当へ発行する。担当は道具で仕事を行い成果物を提出。課長・部長が検収し、他部署へ引き継ぐ。AI社長は実際の成果で優先順位を見直す。原記録と教訓は会社に残る。

例：新商品を試す目的なら、市場調査→商品企画→制作→販売設計→顧客対応→採算確認が一つのプロジェクトとして追跡される。担当社員が停止しても、永続化した仕事と納品物から再開する。

## 2. 組織
| 階層 | 決めること | 自律判断の限界 |
|---|---|---|
| オーナー | 目的、事業範囲、資本、許容損失、外部権限 | 本人が決める委任条件 |
| AI社長 | 事業優先順位、部門計画、継続・縮小の提案 | 許可済み事業と資源の範囲 |
| 部長 | 部門目標、課間の配分、成果検収 | 部門の責任と許可範囲 |
| 課長 | 仕事分解、担当選択、品質確認 | 職務と完了条件の範囲 |
| 担当社員 | 調査、制作、集計などの具体作業 | 登録された道具と対象 |
| 監査役 | 異常指摘、検収、停止 | 自分の権限拡大や本番再開は不可 |

8部は経営企画、マーケティング、商品開発、営業、顧客支援、財務管理、人材・業務開発、情報管理。各部2課・各課1課長1担当。監査役はオーナー直属とする。

## 3. AI社員の実体
AI社員 = 固定社員ID + 職務定義 + 役職権限 + 必要な記録の取得 + 利用可能な道具 + タスク状態 + 成果物 + 評価履歴。
人格や口調は任意の表示設定とする。役職の権限や事実判定を口調に依存させない。
同じモデルを複数職務に利用できる。モデル変更時も社員IDと業務記録は維持する。

社員を休止しても記憶を消さない。職務を更新するときは版を上げ、比較試験を行い、悪化したら戻す。自動の採用・増員・権限拡大は独立した管理変更として扱う。

## 4. 指示と実行
依頼文には目的、対象顧客、入力、制約、担当、検収者、成果物形式、完了条件、根拠、期限、費用枠、停止条件を持たせる。
試作は期限を5分の処理リースとして実装。業務上の納期と優先順位の自動最適化は次段階。
「調査して」だけでなく「対象顧客・出典・反証・未確認事項を整理した調査票を提出」と定義する。

タスク発行と社員の呼出しを区別する。eveの専門社員呼出しで処理を行い、業務台帳で担当・状態・検収を管理する。
社内メッセージの保存は通知・起動そのものではない。相手に処理させる場合は呼出しが必要。

## 5. 検収
担当は自分の成果物を承認できない。上司が検収し、社長の計画は監査役が検収する。
形式検査と内容検査を分ける。形式はコードで必須項目・状態・出典IDを検査。内容は役割を分けた評価、必要に応じ外部結果・テスト・本人確認で検証する。
同じ基盤・同じモデルの別人格は完全に独立した監査ではない。実売上・入金・顧客回答の観測を優先する。

## 6. 会社の記憶
会話、情報源、判断、仕事、成果、費用、評価、知識を分ける。
保存された原記録から関連情報を検索し、その出典を持って仕事に利用する。
原記録をためること、検索すること、モデルの追加学習はそれぞれ別機能。
試作は成果物のキーワード検索と出典IDを実装。埋め込み検索・会話一括取込・教訓の自動昇格は未実装。

## 7. Obsidian
業務台帳を正本とし、Obsidianは人が読める会社の知識画面にする。
社員別、プロジェクト別、仕事別のMarkdownを書き出す。固定IDでつなぐ。
手動編集との競合は更新候補を別ファイルへ保存し、上書きしない。
機密指定された根拠を引用する成果物は本文の書き出しを抑止。秘密情報・個人情報を自動で完全検出できるとは扱わない。
双方向同期、Obsidianの手動編集から業務指示への取込は初期版に含めない。

## 8. 費用と停止
本番では全社→事業→部署→タスクの費用予約を共通台帳で管理する。AIが予算上限を上書きできない。
試作では架空の処理単位の予約・消費のみ実装し、外部支払いAPIは存在しない。
eveのモデル使用量制限は各セッションでの事後検知を含む。全社のリアルタイムな請求上限を保証しない。モデル費用と外部業務費用を混同しない。
本番費用の強制上限は、モデル入口での全社予約・トークン上限・料金表・実績照合を追加してから評価する。

## 9. 運営会議
日常の引き継ぎは文章とタスクで行う。会議は論点、根拠、選択肢、費用、結論、責任者を記録する。
初期は売上変化、品質悪化、費用超過などの例外があるときに開催する。人間の会社の会議数をそのまま増やさない。
日次・週次の報告スケジュールは運用設計として定義し、今回外部の定期実行は登録していない。

## 10. 成果の定義
受注、販売、入金、提供完了、返金、継続を別の事実として扱う。
社員評価は完了件数だけでなく、手戻り、品質、顧客価値、費用、人の介入時間を用いる。
試作のスコアカードはタスク件数・検収・再試行・模擬費用のみ。利益と顧客価値は未測定と表示する。

## 11. 最悪の失敗と対策
| 失敗 | 構造的な対策 |
|---|---|
| 社内報告だけ増え商品が出ない | 成果物と検収を仕事の単位にし会話を有限化 |
| 売れない商品を大量制作 | 支払意思の検証を拡大量産の条件にする |
| 全員が同じ誤りに同意 | 反証・出典・外部の実結果で検証 |
| 複数社員が同じ外部操作 | 一意の操作ID、排他、結果照合。未実装の外部操作は有効化しない |
| 費用が見えない | 予約分を含む台帳。実費未接続は未接続と表示 |
| データをためて誤情報も固定化 | 仮説・検証済み・期限切れを分ける |
| 障害後に何度も繰り返す | 期限、試行上限、検収、停止、履歴から再開 |
| AIが肩書だけで越権 | 道具に実行社員IDを固定しコードで階層を検査 |

## 12. 技術構成
eve 0.83.0、TypeScript、Node.js 24以上、単一端末のSQLite台帳、Markdown書き出し。依存はpackage-lock.jsonで固定。
本番で複数ホストを使う場合はPostgreSQL、永続キュー、認証・権限、機密保管、バックアップ・復元、実費監視が必要。
SQLite台帳をそのまま複数のクラウド実行環境から共有しない。
