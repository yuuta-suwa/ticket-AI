# 記憶・ビッグデータ・Obsidian
## 保存対象の全体像
| 分類 | 内容 | 初期版 |
|---|---|---|
| 会話 | 発言者、時刻、相手、業務目的 | 社内の明示的message記録 |
| 業務 | 指示、担当、状態、納品、検収 | 実装 |
| 情報源 | 入力資料・出典・取得日 | 参考テキストと区分のみ |
| 判断 | 理由、採否、反証、前提 | 検収イベント。事業判断の専用テーブルは後段 |
| 成果 | 注文、提供、入金、返金、継続 | 未接続 |
| 費用 | 予約、消費、請求実績 | 模擬単位の予約・消費 |
| 知識 | 教訓、適用条件、反例、見直し日 | 職務ノートと業務ノート。自動抽出は後段 |

eveの会話セッションはフレームワーク側でも保持される。業務台帳へすべての会話が自動転記されるわけではない。
将来の取込はsession_id、message_id、発言者、時刻、project_id、employee_id、目的、区分、保持期限を付け、重複を排除する。

## 検索
初期は閲覧権限のある仕事の最新版をキーワード検索し、タスクID・成果物ID・モードを返す。
検索にヒットしただけで正しいノウハウとは判定しない。根拠と時期を再確認する。
量が増えたら全文索引、必要に応じたベクトル索引を追加。索引は原記録から再生成可能にする。

## ノウハウ化の基準（本番設計）
仮説→検証→条件を変えた再現→標準手順→再評価→失効。
知識カードは教訓ID、対象顧客、適用条件、根拠、試行数、成果、失敗例、反例、確認日、見直し期限、手順版を持つ。
成功した理由をAIが説明しただけでは標準手順へ昇格しない。相関と因果を分ける。

## Obsidian出力
00_Company：全社・組織。
10_Employees：社員職務と上司。
20_Projects：目的と関連仕事。
30_Work：納品・検収と根拠ID。
90_Conflicts：人が編集した場合の更新候補。
README：入口。

原本はDB。書き出しは固定IDとハッシュで追跡。仮ファイルに書いてから置換し、途中の壊れた本文を出さない。
人の編集があれば元を保持し、更新候補だけ別へ出す。AIが人の修正を自動統合する機能は含まない。
生の会話、根拠本文、顧客一覧、秘密鍵は出力対象にしない。機密を含むタスク名や検収理由を書けば漏れ得るため、実顧客データの本番投入前に全フィールドの分類・閲覧権限を追加する。

## 連携方式
ローカル保管庫へのMarkdown書き出しは基本機能に含む。
公式CLIはデスクトップ操作が必要なときに検討。
Headless Syncはサーバー連携の候補。現時点でベータかつSync契約が必要。同一端末でデスクトップSyncと併用しない。
スマホやクラウドとの同期、端末のObsidian設定変更は今回実施していない。

## 保管・削除（本番設計）
利用目的、必要最小限、保持期限、アクセス履歴、暗号化を設定。
削除は原文・要約・検索索引・埋め込み・ノート派生物へ伝播。バックアップ復元時も削除対象を再適用する。
初期版には削除ワークフローと監査用の改ざん耐性はない。ローカルDBを編集できる本人を敵対者とする設計ではない。
