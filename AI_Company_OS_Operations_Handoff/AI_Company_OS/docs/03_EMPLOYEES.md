# AI社員の仕組み
## 社員台帳
| 項目 | 内容 | 初期実装 |
|---|---|---|
| ID・所属・役職・上司 | 誰が何を担当し誰へ報告するか | 実装 |
| 職務・成果物・評価指標 | 仕事の目的と完了条件 | 実装 |
| モデル・指示文 | 職務を実行する推論基盤 | 定義済み・実推論未検証 |
| 道具と固定実行ID | 誰として何を操作できるか | 実装 |
| 個別仕事と履歴 | 指示、納品、検収、手戻り | 実装 |
| 記憶の取得 | 許可された過去成果物の検索 | キーワード検索 |
| 稼働状態・休止 | 稼働中・待機・休止・退役 | 会社停止のみ実装 |
| 職務版と昇格 | 役割更新、能力比較、権限変更 | 設計 |
| 利益・顧客価値の評価 | 実市場の成果との結び付き | 未接続 |

## 標準指示の構成
役職、使命、担当範囲、対象顧客、入力、成果物、品質基準、利用可能な道具、扱えるデータ、検収者、報告形式、上申条件、過去の根拠を含める。
社員別の指示はdocs/employeesとagent配下に同梱。原本はconfig/organization.jsonと生成スクリプトで追跡する。

## 人格・見た目
通称、顔、口調、得意分野は表示上の拡張として追加できる。人格設定を事実や能力の証明にしない。
まず役職、仕事、成果、記憶が正しく動くことを優先し、アバター・音声は後段に置く。

## 採用（職務の追加）
必要な仕事→既存社員の能力確認→新職務の定義→道具と権限を最小化→模擬評価→限定稼働→結果比較。
社員数の増加を成長指標にしない。処理量、成果、費用、品質の変化で判断する。

## 教育
未達の仕事→原因を入力不足／職務不足／手順不足／道具不足／モデル能力に分ける→手順修正案→過去の評価事例で比較→改善時のみ採用。
同じ失敗例だけに合わせる更新を避け、未見の事例と失敗しなかった既存事例も確認する。
知識の追加とモデルの追加学習を混同しない。

## 評価
処理件数、検収結果、再試行、模擬費用は観測値として集計。
本番の評価は顧客価値、提供品質、利益への寄与、対応時間、根拠の追跡、重大な誤りを加える。
単一の点数を自動生成して採用・昇格を確定しない。根拠と未測定を表示する。

## 休止・交代
社員IDと仕事を永続化し、モデル停止後も履歴は維持。
進行中仕事を照合し、能力と権限を確認した後任へ引き継ぐ。今回は期限切れ処理の回収まで実装し、任意の担当変更は未実装。
